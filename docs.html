Architecture

Service architecture

KubeChan is a microservices system. All components run inside your Kubernetes cluster as standard Deployments. They communicate through Kubernetes CRDs (acting as an internal message bus), a REST API, and WebSockets. No component ever writes to user workloads.

ℹ️
Read-only by design No component in KubeChan has write access to user workloads. The LLM never calls the Kubernetes API directly. Evidence is collected by the diagnostics-worker and passed to the gateway, ensuring secret values are never forwarded.

Incident lifecycle

From anomaly to root cause

Every incident — whether auto-detected or user-reported — goes through the same evidence collection and LLM analysis pipeline. The only difference is how the Incident CRD is created.

Auto pipeline

cluster-watcher continuously reconciles all Pods, Deployments, Services, and Nodes. When a detector fires, it writes a ProblemCase CRD. The CorrelationReconciler walks the owner-reference chain to the workload root and groups ProblemCases into a single Incident.

Manual pipeline

The user opens "+ Report an issue" in the UI, selects the affected resource, writes a description, and optionally tags related resources (Deployments, ConfigMaps, Ingresses, PVCs, Services). backend-api creates the Incident, DiagnosticRun, and analysis request in one transaction.

Needs-more-info loop

When the LLM returns confidence < 0.65, it sets needsMoreInfo: true and returns a list of suggestedResources with reasons. The user can add those resources and trigger a new DiagnosticRun — evidence from both runs is merged before the next analysis call.

Use cases

Real-world troubleshooting scenarios

These are the most common situations where KubeChan provides immediate value.

🔁

CrashLoopBackOff — application keeps restarting

A pod enters CrashLoopBackOff. Normally you'd grep logs, check events, and guess the cause.

1cluster-watcher detects CrashLoopBackOff and creates a ProblemCase CRD within seconds.
2An Incident appears in the UI automatically. Click "Ask KubeChan to help".
3diagnostics-worker collects current and previous crash logs, K8s events, and any mounted ConfigMaps.
4KubeChan's analysis identifies whether the crash is a config error, OOM, missing secret, or application bug — with the exact log line as evidence.
💥

OOMKilled — container killed by memory pressure

Pods are restarting with exit code 137. Resource limits may be missing or wrong.

1CrashLoopBackOff detector fires. Previous container logs capture the OOMKilled exit code.
2Evidence includes pod spec resource limits (or their absence) and ConfigMap values that may set heap sizes.
3LLM pinpoints whether the limit is missing, too low, or set incorrectly via environment variable.
4Recommendation includes the exact resources.limits.memory field to set.
⏳

Pending pod — stuck waiting to be scheduled

A pod has been in Pending for minutes. Could be resource pressure, missing PVC, taint mismatch, or image pull failure.

1PendingTooLongDetector fires after the configured threshold (default 5 min).
2Evidence includes scheduler events, PVC phase and events, and node taints.
3If PVC is the root cause, KubeChan explains the storage class, binding status, and what to check.
4If it needs node information, it requests it via the needs-more-info flow.
🔌

Service has no endpoints — traffic going nowhere

A Service exists but no pod is matching its selector. Requests time out silently.

1ServiceNoEndpointsDetector fires when a Service has zero ready endpoints.
2Evidence includes Deployment status, pod label selectors, and any Ingress rules pointing at this Service.
3LLM compares Service selector with pod labels and identifies the mismatch or missing pods.
4Recommendation shows the exact selector diff to fix.
🖊️

Manual incident — "something is broken but no alert fired"

The cluster looks healthy but your application is misbehaving. No detector fired.

1Click "+ Report an issue". Select the root resource (Deployment, Service, Ingress, etc.).
2Write a description: "Users are getting 502 errors on /api/checkout since the last deploy".
3Optionally tag related resources: the backend Deployment, the ConfigMap, the Ingress.
4Your description is included verbatim in the LLM prompt alongside all collected evidence.
🔄

Re-analysis with augmented context

The LLM returned a low-confidence result and asked for more information.

1A "Needs more info" banner appears in the UI with suggested resource kinds and the LLM's reasoning.
2Click "Add context & Re-analyze". Select the suggested resources from name autocomplete.
3A new DiagnosticRun is created. Evidence from both runs is merged and re-sent to the LLM.
4The new analysis has access to the full combined evidence set and produces a higher-confidence result.

Service reference

cluster-watcher

A Go controller built with controller-runtime. It watches Pods, Deployments, Services, Nodes, and Kubernetes Events. For each reconcile event it runs a set of detectors and writes ProblemCase and Incident CRDs. A per-resource debounce window suppresses noise during rollouts.

Detectors

DetectorWatchesTrigger
CrashLoopBackOffDetectorPodContainer state = CrashLoopBackOff
ImagePullBackOffDetectorPodContainer waiting reason = ImagePullBackOff or ErrImagePull
PendingTooLongDetectorPodPod phase = Pending for > threshold (default 5 min)
DeploymentUnavailableDetectorDeploymentUnavailable replicas > 0 for > threshold (default 5 min)
ServiceNoEndpointsDetectorService / EndpointsService has 0 ready endpoints

Key environment variables

VariableDefaultDescription
DEBOUNCE_WINDOW_SECS30Seconds before re-evaluating a workload after last event
PENDING_THRESHOLD_SECS300Seconds before a Pending pod is flagged
UNAVAILABLE_THRESHOLD_SECS300Seconds before an unavailable Deployment is flagged
CONTROL_NAMESPACEkubechanNamespace where CRDs are written

diagnostics-worker

Reconciles DiagnosticRun CRDs. When a DiagnosticRun appears in pending state, the worker collects a structured evidence payload for the referenced incident's root resource, then POSTs it to backend-api.

Evidence collected per workload

Evidence typeDetails
Pod statusPhase, conditions, container states, restart counts
Current logsLast N lines of stdout (configurable via LOG_TAIL_LINES)
Previous crash logsLast N lines from the previous terminated container (configurable via PREV_LOG_TAIL_LINES)
Kubernetes eventsEvents on the pod and the root resource (Deployment, StatefulSet, etc.)
ConfigMapsAll keys and values (sensitive keys redacted). Includes mount path and env var injection information.
SecretsExistence check only — names collected, values never forwarded
PVCPhase, storage class, capacity, and events
IngressesAll Ingresses in the workload namespace — auto-discovered. Includes rules, paths, backends, annotations.

Key environment variables

VariableDefaultDescription
BACKEND_API_URLhttp://kubechan-backend-api:8080Where to POST evidence
LOG_TAIL_LINES500Lines of current container logs to collect
PREV_LOG_TAIL_LINES200Lines of previous (crashed) container logs
CONTROL_NAMESPACEkubechanNamespace to watch for DiagnosticRun CRDs

backend-api

The central orchestration layer. Serves the REST and WebSocket API for the frontend, stores all state in a local SQLite database (auto-migrated on startup), dispatches async analysis requests to llm-gateway, and broadcasts events to connected clients.

⚠️
Single-writer constraint Set replicaCount: 1 for backend-api. SQLite does not support concurrent writers. Horizontal scaling requires replacing SQLite with PostgreSQL.

llm-gateway

A Python FastAPI service that acts as the stable interface between backend-api and LLM providers. All provider credentials are passed per-request from backend-api — no shared environment-variable credentials are required.

Supported providers

GitHub Copilot GitHub personal access token Any model available through the Copilot API

frontend-ui

A React 19 single-page application served by nginx. It connects to backend-api via REST and maintains a persistent WebSocket connection for live updates.

Key features

  • Incident list with open/resolved sections, sortable by openedAt
  • Expandable details panel: root resource, problem cases, related resources, KubeChan suggestions
  • Live WebSocket updates — "Needs more info" banner appears immediately without a page reload
  • AugmentIncidentModal with name autocomplete for adding related resources
  • KubeChan sidebar: pose transitions (idle → thinking → speaking → chatter), mood system, poke escalation
  • LLM provider settings page — AWS Bedrock and GitHub Copilot, per-user credentials, never returned in GET responses
  • Diagnostics page — list and bulk-delete DiagnosticRuns, expand analysis results
  • Thumbs-up/down feedback on analysis results

KubeChan character poses

PoseWhen shown
idleNo active analysis. Mood level (0–2) affects idle reaction lines.
thinkingDiagnosticRun in progress — evidence being collected or LLM call in flight.
speakingAnalysis complete — 5-section result displayed in speech bubble with confidence badge.
chatterReacting to a WebSocket event (new incident, resolved, poke, rating). Clears automatically.

CRD reference

All CRDs live in the kubechan namespace and use the API group kubechan.io.

Incident

Groups one or more ProblemCases sharing a workload root. Also created directly for manual incidents.

FieldTypeDescription

status.stateenumopen | resolved

Represents a single detected anomaly on a specific resource.

FieldTypeDescription

spec.severityenumcritical | high | medium

A request to collect evidence for an incident. Created by backend-api when analysis is triggered.

Example override file

my-values.yaml
# Tune detection sensitivity
clusterWatcher:
  debounceWindowSecs: 60
  pendingTooLongThresholdSecs: 120

# Collect more logs for verbose apps
diagnosticsWorker:
  logTailLines: 1000
  prevLogTailLines: 500

# Larger DB volume for busy clusters
backendApi:
  storage:
    pvc:
      size: 20Gi

# Enable Ingress for frontend
frontendUi:
  ingress:
    enabled: true
    host: kubechan.example.com
bash
$ helm upgrade --install kubechan kubechan/kubechan \
  --namespace kubechan \
  -f my-values.yaml

Local development with Tilt

For contributors or local experimentation, KubeChan uses Tilt for live-reload development on Docker Desktop Kubernetes.

Prerequisites

Docker DesktoplatestEnable Kubernetes in settings
Tilt≥ 0.33brew install tilt

Go1.25+brew install go

uv≥ 0.5brew install uv

bash — local dev setup
# Clone and enter the repo
$ git clone https://github.com/aryzhykau/kubechan.git && cd kubechan

# Create the SQLite data directory
$ mkdir -p .data && chmod 777 .data

# Switch to Docker Desktop context
$ kubectl config use-context docker-desktop

# Start everything (creates namespace, applies CRDs, runs Tilt)
$ make dev-up
namespace/kubechan created
Tilt started on http://localhost:10350

# UI is available at
$ open http://localhost:30081
💡
Dev overrides Tilt uses helm/kubechan/values-dev.yaml which sets shorter debounce windows (5s), smaller resource limits, and NodePort services for easy local access.
